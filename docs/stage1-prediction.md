# Журнал архітектурних та технічних рішень (Decision Log)

Проєкт: **TelemetryLink**  
Зона відповідальності: **Прогноз**  
Етап: **Зріз 1**

### Рішення 1: Валідація 12-байтового кадру та захист від системних винятків (Fail-Closed)

* **Контекст / Проблема:**  
  Кадр телеметрії має фіксовану бінарну довжину 12 байтів (FORMAT_SPEC_1 §1). Отримання пошкодженого буфера, фрагментованого пакета або даних із некоректними полями (`mode > 7`, `critical > 1`) призводило до ризику викидання необробленого винятку `IndexOutOfRangeException` або спотворення стану наступних компонентів пайплайну.
* **Розглянуті варіанти:**  
  1. *Глушіння винятків:* вилов системного `IndexOutOfRangeException` через загальний блок `try/catch` із поверненням дефолтного об'єкта.
  2. *Неявне коригування:* заповнення полів нулями або обрізання значень за модулем (clamping).
  3. *Сувора попередня валідація (Fail-Closed):* явна перевірка довжини буфера (`Length == 12`) та діапазонів значень полів до початку десеріалізації з генерацією контрольованого `TelemetryValidationException` (або `ArgumentException`).
* **Обране рішення:**  
  Варіант 3. У методі `TelemetryFrame.ReadFrom` реалізовано суворий бар'єр розміру буфера та допустимих діапазонів полів.
* **Чому:**  
  Варіант 1 маскує помилки передачі, а варіант 2 порушує специфікацію бінарного протоколу і вносить фіктивні дані у статистику. Варіант 3 гарантує детерміновану поведінку, захищає наскрізний тракт від аварійного падіння і задовольняє вимогу відсутності витоку винятків індексації.

### Рішення 2: Обробка порожнього вхідного потоку в TelemetryReader (кейс C1.2)

* **Контекст / Проблема:**  
  При подачі на вхід конвеєра порожнього бінарного файлу або потоку нульової довжини (кейс C1.2 специфікації) метод зчитування міг викликати виняток передчасного завершення потоку (`EndOfStreamException`) або повертати неініціалізований стан (`null`).
* **Розглянуті варіанти:**  
  1. Викидання винятку при розмірі вхідних даних менше 12 байтів.
  2. Повернення `null` як сигналу відсутності даних.
  3. Повернення порожньої незмінної колекції (`Array.Empty<TelemetryFrame>()` / порожній `List<TelemetryFrame>`) без генерації винятку.
* **Обране рішення:**  
  Варіант 3. Метод `TelemetryReader.ReadBinary` перевіряє доступність даних у потоці та повертає порожній список при читанні порожнього джерела.
* **Чому:**  
  Порожній потік є валідним граничним випадком роботи системи, а не аварійною ситуацією. Повернення порожньої колекції дозволяє наскрізному пайплайну завершити обробку в штатному режимі без застосування дорогих блоків перехоплення помилок і запобігає `NullReferenceException` у модулях компресії та статистики.

### Рішення 3: Ізоляція семантики прапорця `critical` від моделі класифікації (Методичка §9.22)

* **Контекст / Проблема:**  
  Поле `critical` (байт 11, біт 0) у бінарному кадрі позначає критичність повідомлення. Існував ризик помилкового використання цього прапорця як прямої мітки несправності або класу аномалії вузла.
* **Розглянуті варіанти:**  
  1. Інтерпретувати `critical == 1` як ознаку несправності та призначати аварійний клас (клас > 0).
  2. Відокремити призначення `critical` виключно для семантики пріоритету доставки в каналі зв'язку, а базову заглушку `MajorityClassifier` реалізувати з постійним поверненням класу 0 (Normal) для всіх валідних кадрів.
* **Обране рішення:**  
  Варіант 2. Інваріант класифікатора не залежить від значення поля `critical`.
* **Чому:**  
  Відповідно до розділу 9.22 методички, прапорець `critical` регулює чергу відправки та втрати пакетів у каналі зв'язку, але не підміняє роботу моделі прогнозування. Модель `MajorityClassifier` є базовою заглушкою етапу 1 і повинна повертати домінуючий апріорний клас (0) без евристичних зміщень.

### Рішення 4: Вибір нульового виділення пам'яті (`ReadOnlySpan<byte>` та `BinaryPrimitives`) для парсингу Big-Endian

* **Контекст / Проблема:**  
  Специфікація вимагає десеріалізації багатобайтових чисел у порядку байтів Big-Endian (мережевий порядок), включно зі знаковими значеннями у доповняльному коді (`vibration = -3` як `FF FD`). Стандартний `BinaryReader` у середовищі .NET оптимізований під Little-Endian, вимагає виділення об'єктів у керованій купі (Heap allocations) та ручного реверсу масивів байтів.
* **Розглянуті варіанти:**  
  1. Використання `BinaryReader` з викликом `Array.Reverse()` для кожного зчитаного поля.
  2. Ручні бітові зсуви та маски над байтовим масивом: `(short)((buffer[4] << 8) | buffer[5])`.
  3. Використання методів `System.Buffers.Binary.BinaryPrimitives` (`ReadInt16BigEndian`, `ReadUInt32BigEndian`) поверх `ReadOnlySpan<byte>`.
* **Обране рішення:**  
  Варіант 3. Парсер `TelemetryFrame` приймає `ReadOnlySpan<byte>` і використовує методи класу `BinaryPrimitives`.
* **Чому:**  
  Підхід забезпечує нульові додаткові алокації пам'яті (Zero-allocation), максимальну швидкодію під час обробки високочастотних потоків телеметрії та гарантує коректне знакове розширення для від'ємних чисел (зокрема для температури та вібрації).

### Рішення 5: Фіксація єдиної цільової платформи .NET 8.0 LTS для проектів Solution

* **Контекст / Проблема:**  
  У командному середовищі виникли розбіжності встановлених версій .NET SDK, що спричиняло помилки відновлення пакетів і збої компіляції спільних проєктів `Core`, `Cli` та `Tests`.
* **Розглянуті варіанти:**  
  1. Дозволити кожному учаснику використовувати локальну версію SDK з локальними правками файлів проєктів.
  2. Перевести репозиторій на найновішу версію .NET 9.
  3. Зафіксувати єдиний цільовий фреймворк `.NET 8.0` (`net8.0`) у всіх проєктах рішення (`.csproj`).
* **Обране рішення:**  
  Варіант 3. Усі проєкти рішення переведено на цільовий фреймворк `<TargetFramework>net8.0</TargetFramework>`.
* **Чому:**  
  .NET 8.0 є актуальною версією довготривалої підтримки (LTS), має стабільне середовище виконання, гарантує повну відтворюваність компіляції на машинах усіх учасників команди та забезпечує проходження збірки в автоматизованих перевірках без конфліктів версій інструментарію.
